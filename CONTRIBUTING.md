# Contributing to Communications Sanndbox

Thanks for your interest. This guide covers how to set up the project, make a change, and get it merged.

## Project layout

The repo is one Go module (`communications-sanndbox`, Go 1.23, standard library only) with five independent servers:

| Directory | Service | Port |
| :--- | :--- | :--- |
| `cmd/portal-server` | Portal Hub | `9080` |
| `cmd/email-server` | Email Sanndbox (also SMTP `2525`) | `9081` |
| `cmd/sms-server` | SMS Sanndbox | `9082` |
| `cmd/whatsapp-server` | WhatsApp Business Sanndbox | `9083` |
| `cmd/telegram-server` | Telegram Sanndbox | `9084` |

Each server has the same shape:

- `main.go`: handlers, state, evaluators.
- `templates/index.html`: the single-page UI, embedded into the binary.
- `docs/swagger.json` and `docs/swagger.yaml`: OpenAPI spec generated by [swag](https://github.com/swaggo/swag).

See [README.md](README.md) for the API examples and [TUTORIAL.md](TUTORIAL.md) for a guided tour of each service.

## Getting started

Prerequisites: Go 1.23 or newer. Docker is optional.

```bash
git clone https://github.com/SakariaNdadi/sanndbox.git
cd sanndbox
go build ./...
go run ./cmd/portal-server
```

Run any server with `go run ./cmd/<name>-server`, or run them all with Docker:

```bash
docker compose up --build
```

### Configuration

Only the WhatsApp server reads configuration from the environment. Copy the template and fill in values:

```bash
cp .env.example .env
```

`.env` is git-ignored. Never commit real credentials, tokens, or secrets. Put new settings in `.env.example` with placeholder values only.

## Making a change

1. Open an issue first for anything larger than a small fix, so the approach can be agreed before you invest time.
2. Fork the repo and branch from `master`.
3. Keep the change focused. One concern per pull request. Do not mix refactors with behavior changes.
4. Follow the surrounding code style:
   - Descriptive identifiers, no single-letter variable names.
   - No comments that restate what the code does. Comment only non-obvious constraints.
   - No abstractions beyond what the change needs.
5. If you change handlers or request and response types, regenerate the OpenAPI docs (below) and commit the result.

### Regenerating OpenAPI docs

Install swag at the version the Dockerfile uses, then run it from the repo root for the server you changed:

```bash
go install github.com/swaggo/swag/cmd/swag@v1.16.4
swag init -d cmd/email-server -g main.go -o cmd/email-server/docs --outputTypes json,yaml
```

Replace `email-server` with the server you changed.

## Checks to run before opening a PR

CI runs these on every push to `master` and on every pull request. Run them locally first:

```bash
gofmt -l .          # must print nothing
go vet ./...
golangci-lint run ./...
go build ./...
```

CI pins golangci-lint at v2.15.0. Install the same version to avoid surprises:

```bash
go install github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.15.0
```

There is no automated test suite yet. Test changes by running the affected server and exercising the UI and the `curl` examples in the README. Adding tests is a welcome contribution.

## Commit messages

Use [Conventional Commits](https://www.conventionalcommits.org/) with the service as the scope where it applies:

```
feat(sms-server): add UCS-2 segment counter
fix(email-server): handle closed SMTP connection
docs: clarify WhatsApp .env setup
ci: bump golangci-lint
```

Common types in this repo: `feat`, `fix`, `refactor`, `docs`, `build`, `ci`, `chore`. Keep the subject under about 50 characters and explain the why in the body when it is not obvious.

## Pull requests

- Describe what changed and why, and how you tested it.
- Link the issue it closes.
- Include screenshots for UI changes.
- All CI checks must pass.
- Keep the PR small enough to review in one sitting.

## Reporting bugs

Open an issue with the service affected, the steps to reproduce, the expected result, and the actual result. For the HTTP APIs, include the request you sent and the response you received. Do not paste real credentials or personal data.
